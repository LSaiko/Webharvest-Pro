scraper_engine.py

4-Layer Ethics Pipeline

Most scrapers just fire requests. This one runs four sequential checks before touching the network — URL pattern matching, domain blocklist, robots.txt, and post-fetch paywall detection. Each layer returns a specific reason for any block, making it debuggable and auditable.

defensive programming fail-fast pattern robots.txt RFC compliance
scraper_engine.py
def scrape_url(url: str) -> dict:
  # Layer 1+2: URL + domain validation
  safe, reason = is_url_safe(url)
  if not safe:
    result['error'] = f"BLOCKED: {reason}"
    return result

  # Layer 3: robots.txt + crawl delay
  robots_ok, delay = check_robots_txt(url)
  if not robots_ok:
    result['error'] = f"BLOCKED: {delay}"
    return result

  soup, status, meta = fetch_page(url)

  # Layer 4: paywall scan on response HTML
  for indicator in PAYWALL_INDICATORS:
    if indicator in content_lower:
      meta['error'] = f"Paywall: '{indicator}'"
      return None, meta['error'], meta
index.html — JavaScript

Non-Blocking Async Loop with Rate Limiting

The scraping loop uses async/await for sequential execution while keeping the browser UI responsive. The `&& scraping` guard in the for condition lets the stop button cleanly abort mid-run. Crawl delay is honored between requests using extracted robots.txt values.

async/await cooperative cancellation progressive UI updates
index.html (JS)
async function startScrape() {
  for (let i = 0;
       i < urls.length && scraping;
       i++) {

    // Optimistic UI — show before await
    setTagStatus(i, 'scraping', '...');

    const result = await scrape(urls[i]);

    // Update all surfaces after await
    renderRow(result);
    updateStats();

    // Honor per-site crawl delay
    await sleep(result.crawl_delay * 1000);
  }
}

Interview Prep

Questions Hiring Managers
Will Actually Ask

Real answers — grounded in specific code decisions you can point to.

"Walk me through how this scraper works at a high level." ›

"It's a three-layer pipeline. The first layer is collection — scraper_engine.py handles validation, fetching, and parsing. Before any HTTP request fires, a URL goes through four checks: URL pattern matching for private pages, a domain blocklist, robots.txt compliance, and then after fetching, a paywall keyword scan. If anything fails, the result comes back with success=False and a specific error reason — nothing crashes. The second layer is the result schema — a typed dict that both the scraper and the exporters agree on. The exporters don't know how data was collected; they just consume that shape. The third layer is export — two independent modules: excel_exporter.py for the 8-sheet workbook and csv_exporter.py for the three CSV files. They're completely swappable."

"How did you handle errors and failures?" ›

"Every fetch returns a 3-tuple: parsed content, a status string, and a metadata dict. I never raise exceptions at the scrape layer — failures are just result objects with success=False and an error string. This means the outer loop always completes, even if every URL fails. Failed results still appear in the Excel output with their specific error reasons — paywall detected, robots.txt blocked, connection failed, etc. The caller never needs a try/catch block around the scrape call."

"What would you change if this needed to scale to 10,000 URLs?" ›

"Three main things. First, the current design is synchronous between URLs for rate limiting. At scale I'd use asyncio with a semaphore-controlled concurrency pool — say, 5 concurrent requests — and move rate limiting to a per-domain token bucket rather than a flat delay. The result schema wouldn't change at all. Second, the result list in memory would become a problem. I'd stream results to a SQLite database or a message queue as they come in, so the exporters read from storage rather than a list. Third, I'd add retry logic with exponential backoff for transient failures — currently a timeout just fails immediately."

"Tell me about your choice of data structure for the result." ›

"The result dict is the contract between pipeline stages. I gave it a consistent shape regardless of success or failure — url, timestamp, success, error, data, and meta are always present. data is None when success=False, so all downstream code uses r.get('data') or {} rather than r.get('data', {}) — a subtle difference that handles the case where the key exists but the value is explicitly None. The nested structure inside data also has consistent types: lists are always lists, never None. That means downstream code can safely do len(data.get('headings', [])) without null checks."

"Why vanilla JavaScript for the UI instead of React or Vue?" ›

"This is a single-page tool with no routing, no shared state across components, and a specific requirement: it needs to open as a downloaded HTML file with no server. React requires a build step and a CDN for the runtime; Vue adds weight. Vanilla JS gives me async/await, DOM manipulation, and module-scope state — everything this tool needs — as a single file that works offline. The tradeoff is verbosity: the UI update code is more repetitive than React would be. If this grew to a multi-page app with shared component state, I'd switch to a framework. For a single-file tool, the zero-dependency constraint was worth it."

"What's the most interesting technical challenge you solved?" ›

"The change detection design. I needed to detect if a site's content changed between monitoring runs without storing entire HTML snapshots in browser memory. The solution was content hashing — the Python backend computes an MD5 hash of the raw HTML response, and that 32-character string is stored in the result's meta dict. In the browser, a monitorHashes object maps each URL to its last-seen hash. On the next run, a new hash is computed and compared. If they differ, content changed. If they match, nothing changed. Memory cost is O(number of monitored URLs) rather than O(total bytes of all HTML)."
